# Lab 15 — TaskTracker API
Independent coursework project. No separate frontend; Lab 7 remains the sole main website. No Kubernetes.

## Windows

Use Authorize with username tenant_1_admin or tenant_1_user or tenant_1_user2 or tenant_2_admin; all demo passwords are Lab15Demo! (local lab only). Five tenants each have three demo users. Tokens expire after one hour and are invalidated on app restart unless JWT_SECRET is configured. Port only binds to localhost. Database has no public port. No production security claim; deploy with TLS, DB authentication, secure secret storage, login throttling and real account provisioning before public use.

## 15.1
Schema: tasktracker.tasks {_id,tenant_id,owner_id,title,description,priority,status,created_at}; users {_id,username,tenant_id,role,salt,password_hash}; rate_limits {_id,tenant_id,user_id,count,timestamp}. Tenant is obtained from verified JWT and matched to current DB user. Admin access is within tenant, regular users only own tasks. Atomic per-user per-tenant 30 requests per fixed minute using find_one_and_update, unique _id, TTL expiry at next minute. Fixed windows may allow bursts at boundaries. TTL deletion is asynchronous. Tests reset demo counters and create/delete only marked test tasks; run without concurrent demo API traffic. No arbitrary tenant or owner changes allowed. Swagger login uses OAuth2 form. Test output includes concurrent 429 and real TTL deletion (may take up to 150 seconds).

## 15.2
Separate tasktracker_migration database; shared tasks and tasks_tenant_1 through tasks_tenant_5 are regenerated each run. Seed 500 documents, preserve source and IDs, copy all fields, validate equality and zero cross-tenant records. Benchmarks alternate order, warm up 5 rounds, measure 30 rounds per strategy, include network/driver latency, and exclude cleanup from create timing. Cross-tenant analytics uses $unionWith. No fabricated timings or presumed winner. Evidence JSON/CSV in evidence/. Both lab activities are included in the published image.

## Recommendation
Shared collections suit many tenants, frequent cross-tenant analytics and uniform schema/index migrations; compound tenant indexes and mandatory tenant filtering are essential. Collection-per-tenant can simplify tenant-specific indexes, collection-scoped backup/restore and targeted schema changes, but increases collection/index overhead and migration coordination. Collection boundaries alone do not guarantee security or regulatory compliance; enforce access controls, and consider database-per-tenant or separate deployments for stronger isolation. Compare actual timings: 500 records on one local MongoDB server are not a production scalability claim. Migration is an offline controlled copy, not a live cutover; production would require write coordination, validation and rollback planning.
